## What this is

A static GitHub Pages site (`/docs`) that replaces the HubSpot CMS pages on `sales.fairbankequipment.com`. Reps use it for product inquiry (pricing and stock) and order placement. Every HubSpot and Eclipse call goes through n8n webhooks on `n8n.fairbankequipment.com`. The original HubSpot app (deal-based CRM card plus two serverless functions) is symlinked at `eclipse-branch-selector/` for reference only. It is read-only.

## Sign-in (`docs/auth.js`)

Sign in with HubSpot (2026-10-19, on request, branch `feature/hubspot-login`: "confirm 1000% that the user is logged into HubSpot", without Microsoft login). Replaces the shared password gate. **Not live yet:** needs the HubSpot app, two n8n credentials and the client id (see "Going live with HubSpot sign-in" below). The site and the flows must ship together: once the webhooks require the token, the old `auth.js` can no longer call them.

How it works:
1. Locked page: `html.fb-locked` hides every `body` child and shows a "Sign in with HubSpot" button (same dark gate style as before).
2. The button makes a random nonce (kept in `sessionStorage["fb_nonce"]`) and sends the browser to `https://app.hubspot.com/oauth/43793456/authorize` (pinned to Fairbank's account) with `client_id`, `redirect_uri` (the n8n flow), `scope` (the app's seven scopes, space-separated, see below) and `state` = base64url(JSON `{ r: current URL without the fragment, n: nonce }`).
3. HubSpot logs the rep in (or uses their existing HubSpot login), asks for consent, and sends the browser to the n8n flow `auth-hubspot` with a one-time `code`.
4. The flow (see below) proves the login with HubSpot and redirects back to `r` with `#fb_session=<JWT>&fb_nonce=<n>`, or `#fb_auth_error=<message>`.
5. `auth.js` accepts the session only if the nonce matches the one this tab stored (a link with someone else's token is ignored), the token's `hub_id` is `43793456`, it has an `e_user_id` and it has more than 30s left. It stores it in `localStorage["fb_session"]` and strips the fragment with `history.replaceState`.

Then:
- `window.FB_USER` is built from the token's claims: `{ e_user_id, name, email, default_branch, territories, default_territory, hs_user_id, hs_owner_id }` (`territories`, an array, and `default_territory` replaced `territory` on 2026-10-22; a token signed before then has `[]` and `""` until its next refresh). `window.fbSignOut()` and the "name · Sign out" chip are unchanged (the order page hides the chip and uses its own header menu). The `fb:auth` event is no longer fired: a signed-in page is always signed in when `auth.js` finishes, because the return from HubSpot is a full page load.
- **`branch_region` (2026-10-23, on request):** `window.FB_USER.branch_region` is the HubSpot user property `branch_region` ("AG Plains", "AG West" or "LP", per the user), read from the token's `branch_region` claim. Order placement uses it for the minimum markup (see **Minimum price**). The repo copies of auth-hubspot, auth-refresh and user-lookup read and return it. **auth-refresh and user-lookup are live** (pushed through the n8n connector and published 2026-10-23, on request; auth-refresh active version `0c34ce0c-a0f3-44c7-9a13-12e099306998`, user-lookup `34ed2cc8-20f1-4c15-aacf-905f764d2156`; the live Code nodes matched the repo before the change). **auth-hubspot is not**: the user is changing it by hand (MCP access is off there). ### v1-inventory-lookup (`POST v1/inventory-lookup {dealId}`)
This is a port of `eclipseInventoryLookup.js`, and the response body has the same shape.
1. HubSpot deal Get.
2. The `dealstage` property definition, which maps the stage id to a label. The node has no pipelines resource.
3. Blocked-stage gate, then missing-OID gate.
4. Deal → line items association, then Batch Read of the line items, then the missing-product-ID gate.
5. Eclipse SO Get to find the bill-to customer, which pricing needs. The bill-to is per generation: `results[0].generations[].billToId`. The flow uses the gen from the deal's `e_sorder_id` suffix, else the first gen (verified against S0920344.0001 → 62938, 2026-10-17).
6. Eclipse Product Inventory Pricing Inquiry (`considerUserAuthBranch: true`, `allInOne`).
7. The `Build branch matrix` node holds the original `BRANCH_COORDS`, haversine, branch matrix, unavailable products and `findClosestCombination`, unchanged.

### v1-place-order (`POST v1/place-order`)
This is a port of `eclipsePlaceOrder.js`, with the same stage order and the same idempotency:
1. HubSpot `e_sorder_id`, then preflight: the order ID must carry the gen suffix.
2. Eclipse SO Get, then `Plan generations`: reuse a matching gen, otherwise create one.
3. Create Shipment for each new gen, then `Plan line ops` (Pass A on destination gens, Pass B on the source gen).
4. POST line items, then DELETE, then PUT qty. Each step is skipped when its list is empty.
5. Re-read the order and cancel gens that ended up empty (best-effort).
6. `update-hs-deal` with every touched gen in one call. This replaces the dead Celigo export.

`Final` returns `{ success, eclipseOrderId, createdGenerations, eclipseResponses }`.

The planning code was checked against a mocked order and gave the same POST, DELETE and cancel plan as the original.
